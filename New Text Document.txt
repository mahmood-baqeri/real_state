این پروژه نباید به یک پنل مدیریت معمولی، مجموعه‌ای از صفحات CRUD یا یک قالب آماده Admin Dashboard تبدیل شود.

**هیچ‌یک از قابلیت‌های تعریف‌شده در این سند نباید صرفاً به دلیل بزرگ بودن پروژه حذف، ساده‌سازی یا به Mock تبدیل شود.**

# بخش دوم: قوانین اساسی و غیرقابل‌تغییر پروژه

موارد زیر الزامات قطعی هستند و نباید بدون تأیید صریح کاربر تغییر کنند.

## 2.1. معماری Backend

فناوری‌های قطعی:

- Python
- Django
- FastAPI
- PostgreSQL
- Redis
- Celery
- WebSocket در صورت نیاز

معماری باید به این صورت باشد:

### Django Core

Django تنها مرجع معتبر برای موارد زیر است:

- Database Models
- Migrations
- Domain Services
- Business Logic
- Business Rules
- Transactions
- Multi-Tenancy
- Database Operations
- Business Workflows

### FastAPI Core

FastAPI لایه ارائه API به Frontend است.

تمام APIهای موردنیاز Frontend باید از طریق FastAPI ارائه شوند.

FastAPI نباید محل اصلی پیاده‌سازی منطق تجاری باشد.

FastAPI باید از Django ORM و سرویس‌های Django استفاده کند.

قواعد:

- راه‌اندازی Django با `django.setup()` در چرخه عمر مناسب FastAPI
- استفاده صحیح از `sync_to_async` یا `run_in_threadpool`
- رعایت Thread Safety
- مدیریت صحیح Database Connections
- مدیریت تراکنش‌ها
- استفاده صحیح از `close_old_connections()`
- جلوگیری از اجرای ناامن ORM همگام در مسیر Async
- مدیریت صحیح Event Loop

استفاده از SQLAlchemy یا ORM مستقل و موازی ممنوع است.

**Django REST Framework (DRF) مطلقاً ممنوع است.**

هیچ‌یک از موارد زیر نباید در پروژه وجود داشته باشند:

- DRF
- DRF Serializers
- DRF ViewSets
- DRF Routers
- DRF Permissions
- وابستگی‌های مربوط به DRF
- معماری مبتنی بر DRF

تمام APIها باید با FastAPI و Pydantic پیاده‌سازی شوند.

## 2.2. ساختار قطعی Backend

ساختار Backend باید به شکل زیر باشد:

```text
backend/
├── django_core/
│   ├── config/
│   ├── apps/
│   ├── core/
│   ├── services/
│   ├── manage.py
│   ├── requirements/
│   └── ...
│
└── fastapi_core/
    ├── app/
    ├── api/
    ├── dependencies/
    ├── schemas/
    ├── middleware/
    ├── services/
    ├── tests/
    └── main.py
```

مسیر قدیمی:

`backend/fastapi`

باید به‌صورت کامل با مسیر زیر جایگزین شود:

`backend/fastapi_core`

این تغییر باید در تمام پروژه اعمال شود:

- پوشه‌ها
- Importها
- Environment Variables
- Configuration
- Docker
- Docker Compose
- Commands
- Scripts
- Tests
- CI/CD
- Documentation
- Deployment
- مسیرهای اجرای برنامه

هیچ Import، تنظیم یا مسیر قدیمی نباید باقی بماند.

## 2.3. PostgreSQL تنها دیتابیس مجاز

PostgreSQL تنها دیتابیس مورد تأیید پروژه است.

استفاده از SQLite در موارد زیر ممنوع است:

- Development
- Testing
- Staging
- Production

قواعد:

- Django مالک Models و Migrations است.
- FastAPI از همان Django ORM استفاده می‌کند.
- تمام تست‌ها با PostgreSQL اجرا می‌شوند.
- Constraints و Foreign Keys اصولی طراحی می‌شوند.
- Indexها متناسب با Queryها ایجاد می‌شوند.
- تراکنش‌ها به‌درستی مدیریت می‌شوند.
- Connection Management اصولی باشد.
- برای اطلاعات مالی از Decimal استفاده شود، نه Float.
- تنظیمات دیتابیس برای محیط‌های مختلف مستند شوند.

پروژه بدون PostgreSQL نباید به‌عنوان نسخه معتبر و قابل اجرا تلقی شود.

## 7.6. تست‌های امنیتی اجباری

سناریوهای زیر باید واقعاً تست شوند:

1. کاربر Tenant A نباید اطلاعات Tenant B را ببیند.
2. تغییر شناسه در URL نباید دسترسی غیرمجاز ایجاد کند.
3. کاربر نتواند Role خود را ارتقا دهد.
4. کاربر غیرفعال نتواند از Refresh Token استفاده کند.
5. نشست باطل‌شده معتبر نباشد.
6. کاربر فاقد مجوز نتواند عملیات مالی انجام دهد.
7. فایل غیرمجاز یا مخرب رد شود.
8. درخواست‌های بیش از حد محدود شوند.
9. عملیات حساس در Audit Log ثبت شوند.
10. دسترسی به شعب مختلف مطابق مجوزها باشد.

تست‌های امنیتی حیاتی باید در CI اجرا شوند و شکست آن‌ها مانع انتشار شود.

**هیچ سیستمی را غیرقابل نفوذ معرفی نکن. هدف، اجرای کنترل‌های امنیتی عملی، آزمون‌پذیر و قابل ممیزی است.**

- برای Dashboard و Reports قابل استفاده باشند.
- برای تست Tenant Isolation مناسب باشند.

داده‌های مالی باید از نظر حسابداری معتبر و متوازن باشند.

## 8.3. قواعد Seeder

1. Idempotent باشد.
2. اجرای مجدد داده تکراری ایجاد نکند.
3. روابط معتبر حفظ شوند.
4. داده‌های آزمایشی قابل شناسایی باشند.
5. پاک‌سازی کنترل‌شده داشته باشد.
6. اطلاعات واقعی را حذف نکند.
7. اجرای آن در Production ممنوع باشد.

دستور اصلی:

```bash
python manage.py seed_demo
```

دستور پاک‌سازی:

```bash
python manage.py clear_demo_data
```

برای پاک‌سازی، تأیید صریح و محدودیت محیط اجرا در نظر بگیر.

## 8.4. حساب‌های آزمایشی واقعی

برای تمام نقش‌های اصلی حساب واقعی در PostgreSQL بساز:

- Super Admin
- مدیر آژانس
- مدیر شعبه
- مشاور
- حسابدار
- پشتیبان
- کاربر عادی
- سایر نقش‌های ضروری

هر حساب باید دارای موارد زیر باشد:

- Username یا Email
- Password
- Role
- Tenant
- Branch
- Permissions
- وضعیت فعال بودن

ورود باید از همان صفحه Login و همان API واقعی پروژه انجام شود.

Mock Authentication، ورود نمایشی یا دور زدن احراز هویت ممنوع است.

حساب‌ها فقط در Development فعال باشند.

رمزهای آزمایشی نباید در Production فعال یا منتشر شوند.

مستندات حساب‌ها باید شامل اطلاعات لازم برای ورود و نقش هر حساب باشد.

# بخش دوازدهم: سیستم مدیریت وضعیت و گزارش پیشرفت

برای تمام قابلیت‌ها وضعیت مشخص ثبت کن.

وضعیت‌های مجاز:

- Not Started
- In Progress
- Implemented
- Tested
- Verified

معنای وضعیت‌ها:

**Not Started:** هنوز شروع نشده است.

**In Progress:** در حال توسعه است.

**Implemented:** کد قابلیت نوشته شده است، اما لزوماً تست نشده است.

**Tested:** تست‌های مربوطه اجرا شده و نتیجه موفق داشته‌اند.

**Verified:** علاوه بر تست، عملکرد واقعی، اتصال، مجوزها، رفتار رابط کاربری و معیارهای پذیرش بررسی شده‌اند.

هیچ قابلیتی را بدون شواهد کافی Tested یا Verified اعلام نکن.

برای هر قابلیت ثبت کن:

- نام قابلیت
- وضعیت
- فایل‌های مرتبط
- API مرتبط
- مدل‌های دیتابیس
- تست‌های مربوط
- مشکلات باقی‌مانده
- معیار پذیرش
- نتیجه بررسی

در پایان هر فاز، گزارش پیشرفت ارائه بده.
